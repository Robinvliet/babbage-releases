Self-hosting

Web version

The web version runs Babbage as an ordinary web app on http://localhost:3000, reachable only from the machine it runs on. This is also the route to your phone, see On your phone.

You need the source code. It is not on the download page: that page ships the installers for the desktop app.

With Docker

Requirement: Docker is installed.

cp .env.example .env
docker compose up -d --build

Then open http://localhost:3000.

Commands you will use:

Command Does
docker compose up -d --build build and start, after code changes
docker compose up -d start without rebuilding
docker compose logs -f follow the logs live
docker compose restart restart
docker compose down stop and remove the container

Your data lives outside the container, so docker compose down is safe: nothing is lost. See Data and backup.

The date the agent gets with every reply follows the container's clock, which is UTC unless you uncomment the TZ line in docker-compose.yml and set your own time zone, for example Europe/Amsterdam.

Without Docker

Requirement: Node 20 or newer.

npm install
npm run build
npm run start

Then open http://localhost:3000.

The first time

On your first visit the web version asks you to set a password, at least eight characters. After that you log in with it. Right after the first login comes the same setup as in the desktop app, see First steps.

That first screen also asks for the Setup token, so that only someone who can open the files on this computer sets the password. Babbage makes the token when it starts without a password and writes it to .env as BABBAGE_SETUP_TOKEN: with Docker the .env next to docker-compose.yml, without Docker the .env in the project folder. The server log says so in one line, without the token itself. Copy the value after the = into the field. Once the password is set, Babbage removes the token from .env.

That password exists because the web version can be reached by several devices through Tailscale, unlike the desktop app which only exists on your own machine. The port itself is reachable only from that machine by default (127.0.0.1).

Settings you may want to change, such as the port or where your data lives, are on Configuration. Open the web version on another address than localhost or 127.0.0.1, such as your Tailscale address, and you add that address there first (BABBAGE_ALLOWED_HOSTS).

Updating

git pull
docker compose up -d --build

Without Docker: npm run build && npm run start.

Database migrations run automatically at startup, so there is nothing to do for those.

Coming from 0.23.2 or older

Version 0.24.0 renames the app from Omnissiah to Babbage, and with it the Docker service, the database file and the OMNISSIAH_* settings. Nothing moves by itself. A plain git pull followed by docker compose up -d --build leaves the old omnissiah container running on the port and starts a fresh Babbage with an empty database next to your old one, so do this once instead:

  1. Stop the old container first: docker compose down, before you run up again. Without Docker: stop the running npm run start.
  2. In data/, rename omnissiah.db to babbage.db, and omnissiah.db-wal and omnissiah.db-shm too if they are there.
  3. In .env, rename every key that starts with OMNISSIAH_ so that it starts with BABBAGE_, keeping the values: OMNISSIAH_AUTH_SECRET, OMNISSIAH_DATA_DIR if you set it, and each OMNISSIAH_CUSTOM_KEY_… (the key of a custom endpoint). The provider keys stay as they are. If you exported OMNISSIAH_DATA_DIR in your shell or a service file rather than in .env, rename it there; the old name is simply ignored and the data folder falls back to the working directory.
  4. To keep the folder snapshots of linked folders, rename omnissiah to babbage in data/snapshots/store/refs/ while that folder still contains files.
  5. docker compose up -d --build, or npm run build && npm run start. The container is now called babbage.

If you skipped the session secret, the server creates one at its first start and writes it to .env; no restart is needed.
