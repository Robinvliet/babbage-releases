Working with Babbage

Working in a folder

Link a folder to a conversation and the agent can work in it: look around, read files, and if you allow it, write, run commands and run scripts. There is no mode to switch on for this; what it may do follows from three things you can see - whether a folder is linked, whether that folder is read-only, and the approval level. Without a folder it is not idle: it works in a workspace of its own, away from your files.

With tools it works in several steps in a row: plan, use a tool, look at the result and carry on. Twenty steps per turn at most.

First link a folder

You link one with Work in a folder in the bar under the input bar, or with Add folder in the menu next to it. What you get to see before you confirm is on Sources.

With a folder linked, the tools View folder, Read file, Write file, Terminal and Script work in that folder. Without one they are not gone: they work in the conversation's own workspace instead, and your own files stay out of reach.

You can link several folders at once. Every folder has a name, and in the action timeline you see per step which folder it happened in.

On Windows the terminal uses Git for Windows: commands run in Git Bash, so the same shell syntax works on every platform. Without it, Babbage offers to fetch a portable copy of it (57 MB, into your user folder, without administrator rights, and removable again from Settings), or you install Git for Windows yourself.

Without a folder: the workspace

A conversation that is allowed to write gets a scratch folder of its own, inside the Babbage data folder under data/scratch/, one per conversation. Nothing is created up front: the folder appears the first time the agent writes a file or runs a command there. From that moment a chip Workspace sits in the bar under the input bar; click it to show the folder in the Finder or Explorer. The agent knows the path and is told to name the file when it leaves something there for you, such as a converted document or the output of a script.

The workspace belongs to the conversation. Delete the conversation and the folder goes with it, including the snapshots the terminal made in it. A conversation you start from another one with Continue from here begins with an empty one.

With a linked folder the workspace stays out of the way: the agent works in your folder, and the workspace only comes along if it already existed before you linked the folder. In that case both exist side by side and every action says which of the two it happened in.

One thing changed with this for older conversations. Version 0.21.0 set every conversation from before the read-only setting that was not an agent conversation to read only, to keep the guarantee its old mode gave. That setting is about linked folders and only appears once one is linked; a conversation without a folder now has the terminal and scripts again, in its workspace, under its own approval level, which is Approve manually unless you changed it.

Asking for a folder

The agent does not have to wait for you to link something. It may name a folder outside the linked ones, with a full path or one that starts with ~, and Babbage then asks you. What the card says is what happens when you approve:

  • Reading. "The agent wants to read ~/Downloads, which is outside the linked folders. Approving links that folder read-only to this conversation: it appears as a chip in the bar under the input field, and later reads there no longer ask." The agent is told to ask for the folder once, not for every file.
  • Writing. "The agent wants to write in ~/Pictures/Holiday 2026, which is outside the linked folders (the folder does not exist yet and is created on approval). Approving links that folder with write access to this conversation." Writing outside the linked folders asks in every approval setting, Skip approvals included.
  • Writing in a read-only folder. "The agent wants to write Holiday-check/a.jpg in Pictures, which is linked read-only. Approving switches ~/Pictures to read and write for this conversation." One card, and the chip changes with it.

Reading follows the approval level: Approve manually asks every time, Approve automatically links a folder under your home folder without asking and asks for anything else (your home folder itself, system folders, other users, external volumes), Approve smartly lets the helper model judge, and Skip approvals links without asking. Some paths are refused whatever the level; see What never goes through. A folder that contains a folder you already linked is not linked this way; you link that one yourself with Add folder, where you get to choose what it replaces.

A scheduled task cannot ask: a run that wants to reach outside its linked folders pauses and waits for your approval in the task conversation, and a sub-agent gets a refusal that names the folder, so the main conversation can ask you instead. In a project with Answer only from the sources the question does not exist at all.

Read only, or read and write

Every linked folder carries its own access, and the chip shows it: nothing for read and write, read-only for a folder the agent may only look at. Open the chip menu, or the folder's menu in the sources panel, and switch it. A folder you link yourself starts on read and write; a folder the agent asked to read starts read-only, a folder it asked to write to starts with write access.

Next to the folder chips sits a second setting, and it wins over the access per folder:

  • Read and write. "The agent may edit files and run shell commands in the linked folders, under the approval level."
  • Read only. "The agent can read the linked folders but cannot change anything: no file edits, no shell, no scripts."

Reading is always allowed once a folder is linked. On Read only the writing tools are not narrowed but absent: they are not in the turn at all, so there is nothing to approve and nothing to go wrong, and the same holds for a sub-agent it farms work out to. With a single read-only folder the agent still gets its writing tools, in the conversation's own workspace, so that work has somewhere to land. A new conversation starts on read and write; conversations from before this setting kept exactly the permission their old mode gave them.

What happens without asking

Next to the + on the input bar sits the approval level. There are four settings, and they apply per conversation:

  • Approve manually. "The agent pauses so you can approve every action." This is the default.
  • Approve automatically. "The agent works on its own and only pauses for something risky."
  • Approve smartly. "A helper model reviews every action and only pauses what it does not trust."
  • Skip approvals. "The agent never pauses, not even for risky actions."

The level applies to writing files, the terminal, scripts and tools from MCP servers, in every conversation. Things that only land in the app itself, such as putting something in your sources or your memory, fall outside it.

When the agent pauses, the proposed action appears in full in the chat, with the line that nothing is saved until you approve, and two buttons: Approve and Reject. There is no "always allow"; that is what the levels above are for.

An identical call you already approved in this conversation does not pause a second time. The timeline says so on that step, so an action that goes through without a question is never silent about why.

If the agent delegates a subtask to a sub-agent, every action that needs approval is automatically refused there, and that is stated in the summary you get back.

Two safety nets that always run

They work in every setting, including Skip approvals.

Before a file is overwritten Babbage keeps the old version. Under that step you then find Restore, and afterwards: "Restored to the version from before this change." At most twenty versions per file are kept, for thirty days, and only for files up to 10 MB. If a file is too large for such a copy, the Automatic level pauses for the overwrite after all.

Before the first far-reaching command of a turn Babbage takes a snapshot of the whole working folder. Restoring asks for confirmation, and that dialog says exactly what happens: "Files created after the snapshot stay. Before restoring, the current state is captured too, so the action is reversible." There is one case where restoring does remove files, and the dialog says so instead: when the folder was empty at the moment of the snapshot - a fresh conversation workspace, for instance - everything in it was created afterwards, so restoring empties it again. Files Babbage never snapshots anyway (.env, node_modules, anything over 10 MB) stay put even then.

Documents are not overwritten with text

Word files, spreadsheets, PDFs and images are containers, not text. Writing plain text over one of them produces a file that no longer opens. That is now refused, in every approval setting, before the safety net above even comes into play: "Refusing to write plain text over …: the existing file contains binary data."

The message also says what does work: change such a document with a library through the terminal or a script, for example python-docx or openpyxl, or delete the file first to replace it entirely. Creating a new file is never refused; there is nothing to destroy yet.

What never goes through

Some commands are refused unconditionally, in every approval setting, and no setting lifts that. Think of formatting a file system, recursively deleting a system folder or your home folder, shutting the machine down, and touching the database or the .env of Babbage itself. The message says the agent should not try again and should not work around it either. If you really want such a thing, you run it yourself in your own terminal.

Secrets are on a fixed list, and that list works in both directions. The agent never reads, lists or writes ~/.ssh, ~/.gnupg, ~/.aws, ~/.netrc, ~/.npmrc, ~/.pypirc, ~/.git-credentials, any .env file wherever it is (.env.local and the like included; only .env.example, .env.sample and .env.template are exempt, they are templates by convention), or Babbage's own database, .env and skills lockfile. That holds inside a linked folder too, for the file tools and for the terminal, and the terminal refuses any command that so much as mentions such a path, so ssh -i ~/.ssh/key host or cp .env.example .env are refused as well. The message tells the agent that you can paste the content yourself, or run that one command in your own terminal.

If your API keys happen to end up in the output of a command, a placeholder takes their place - [GEMASKEERD], one of the few strings that is still Dutch - and the child process does not get them in the first place.

Be honest about what this is

Those safety nets and levels prevent accidents; they are not a security boundary. The real boundary is your operating system, and on a Mac and on Windows Babbage now uses it. Terminal commands, monitor commands and scripts run inside an operating-system sandbox: they can write only in your linked folders and the workspace, cannot read anything on the secrets list, and cannot change git hooks or shell startup files. You switch it under Settings, Tools, with Run commands in the sandbox, and every terminal and script step says which of the two it was, sandbox or outside the sandbox. Whatever the sandbox held back, a blocked host or a refused write, is listed under Sandbox on the System tab of the Command Center, even when the command itself reported success.

Be precise about the edges, because a boundary you misread is worse than one you know you do not have:

  • On Windows it is a separate account, set up once. The sandbox there is a local Windows account named BabbageSandbox that Babbage creates when you ask for it: a card on the empty page the first time, or Set up the sandbox under Settings, Tools. Windows asks for administrator rights once, and once more if you ever choose Remove the sandbox. That account can read and write only the folders you link, the workspace and Babbage's own folders (listed under Readable for the sandbox), so on Windows reading outside those folders fails with "Permission denied" too, and the usual answer is to link the folder, read-only if reading is all you need. Folders you link stay reachable for commands in every conversation until you quit Babbage; on a Mac each command sees only the folders of its own conversation. Terminal commands, monitor commands and scripts all run inside it. Two edges to know: the first command in a conversation waits a moment while its folders are made reachable (the step says so), and a command that was refused but ended without an error message leaves no trace on the step, because on Windows Babbage reads refusals from the command's own output.
  • On a Mac, macOS guards some folders itself. macOS may ask once for access to your Desktop, Documents or Downloads folder; that prompt is macOS's, not Babbage's, and if you decline it, a command that needs the folder fails with "Operation not permitted" and the agent is told that macOS refused it, not the sandbox, and where you can still allow it: System Settings, Privacy & Security, Files & Folders. The step itself shows the same refusal in a line underneath it, naming the folder where it can, so you see it even if the agent does not pass it on. When the agent reads such a folder with Babbage's own file tools instead of a command, that is reported as refused as well, not as an empty folder. The line in that prompt explaining why Babbage asks follows the language of macOS, not the language you chose in Babbage: Dutch on a Mac set to Dutch, English otherwise.
  • The file tools are not inside it. Reading and writing files happens inside Babbage itself rather than in a command it starts, so there the guards, the read-only setting and the approval level are the whole story.
  • MCP servers are not inside it. A local server is a process of Babbage itself, not a command from a conversation, so only add servers you trust. See MCP servers.
  • A command cannot open a port for others. Listening for incoming connections is refused; that is part of the boundary, not a defect.
  • A command cannot drive your other apps. Sending Apple events, which is what open and osascript do, stays closed on purpose: opening that door would let a command reach everything those apps can reach.

So still do not link a folder whose contents you would not want to lose without a backup. More about that is on Privacy and security.

When a command needs the internet

Inside the sandbox a command starts with no way out. If it tries to reach a host anyway, the attempt fails, the step names the host, and the agent is told to tell you rather than to try again or find another route. A card above the input field then offers the choice, per host, and stays until you choose or run another command; what you chose is kept on that step in the timeline:

  • Once allows it for the next command in this conversation that actually needs it; a command that does not reach that host leaves the permission standing.
  • This conversation allows it for the rest of this conversation.
  • Always allows it everywhere, until you remove it.

One more row sits underneath, Run outside the sandbox, for when the domain is not the point and the command simply needs the machine: For this reply, This conversation or Always. Mind the first one: it covers every terminal command and script in that reply, not just the one that was blocked, because the agent picks its shell once per reply. The second shows as a chip under the input field, Outside the sandbox, for as long as it holds; its menu has one item, Back in the sandbox. Nothing is retried for you: after you choose, ask the agent to run the command again.

The same card appears when the sandbox refused a file action, a write outside your linked folders or a git init, say: it names the action and the path ("writing to ~/Desktop/notes.txt") and offers only the Run outside the sandbox row, because the sandbox has no finer way to let a shell command through. When one step was blocked on both counts, the card shows both lists.

Two things are already allowed without asking. Your local model server is one of them, because otherwise a command could not reach the model running next to it; Settings, Tools shows it under Allowed by Babbage, and it follows the base URL you set under Models. The other is whatever you put on the Always allowed list yourself, which is the same screen, and the only place you can take an entry off again.

Scheduled tasks and monitors are deliberately stricter: they only get the always list. A rule you allowed for a conversation does not apply there, because nobody is watching to answer for it. A blocked host, in a monitor check or in a terminal step of the run itself, shows up as a warning on that run, naming the host, with an Allow always button next to it that puts the host on the always list; the card in the task's conversation offers only Always for the same reason.

Where changing things does not exist

In a project with Answer only from the sources nothing on your disk can change, and scheduled tasks cannot run either. Reading a linked folder is still allowed there, and it is even one of the ways an answer gets its source reference. What falls away is writing, the terminal, scripts and sub-agents: those produce content that is not a source, and the promise could then no longer be kept. See Projects.
